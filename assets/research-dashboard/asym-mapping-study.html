Asymmetric D2D links · co-fit campaign (HW fitted to each workload's traffic)

Current campaign only (from 2026-10-18). Each workload: the HW is fitted to its ring-mapped traffic, mappings are re-searched on that HW, repeated until converged; speedup is against uniform HW with the best of every mapping type. Everything published before 2026-10-18 01:55 (per-workload graphs, ablation, forwarding sensitivity, fast-path groups) is in the Backup · asym study 2026-10-18 01:55 tab. Sections without new data stay empty until the campaign reaches them.

Goal: with the same total D2D capacity as uniform 256 B/cycle/link, find K=2 asymmetric tile designs that run faster on all 16 workloads (9 CNN, 2 RNN, 5 Transformer) at batches 1/4/16. Every source TX equals the adjacent RX, no boundary D2D port is left unconnected, rotations only. Speedup = (best uniform cycles / asymmetric cycles − 1) × 100%. The uniform side is the fastest native-validated uniform result from any study, and it always receives the same added mapping search.

1. HW constraints (all arrays)

Tiles are reused by rotation only, so links fall into width groups. Wider in one direction means narrower in the other (fixed total).

  • Same total D2D capacity as uniform (256 B/cycle per directed link).
  • Reusable tiles, rotation only (no mirrored tiles). K = number of tile kinds: C4/C8 K=2, C9/C15/C16/C32 K=3 (corner, edge, interior).
  • Every TX width equals the adjacent RX width. No boundary port left unconnected.
  • Widths in 64 B/cycle modules (uniform link = 4 modules per direction).
  • These rules tie links into equality groups. A design is one width per group (HW name = widths in group order).

4. Findings

  • Asymmetric links pay off when D2D traffic keeps one direction across segments and that direction matches the tile rotation (single perimeter ring: C4, C8, C15).
  • An interior ring (C16) carries nearly symmetric traffic, so moving capacity into one direction hurts the other.
  • DRAM placement matters: rotation-symmetric DRAM (mid-side) helps C9 and C16 compared with left/right DRAM.
  • Batch 16 is the weakest batch everywhere (DRAM-bound share grows).

What was added to the mapper

All methods extend Gemini's mapper (DP layer grouping + simulated-annealing spatial mapping). Each is a cumulative ablation level: a level's candidate pool is the union of every mapping found so far, re-evaluated on every K=2 width design, so a level only adds options. Figures use the C8 2×4 array; chip numbers follow the simulator.

K=2Asymmetric design space

With K=2 tiles, matched TX/RX and no reflection, C8 has exactly three width groups: c = one ring direction (“cw”, 8 links), a = the opposite ring direction (“ccw”, 8 links), b = middle cross links (4). 8a + 4b + 8c = 5120 B/cycle → 3,081 designs, all evaluated. Asymmetry pays off only if traffic prefers one ring direction.

L0Baseline search + coherent partition

Gemini’s search with chiplet-swap and tensor-order moves, plus coherent tensor-partition placement (a layer’s partitions stay chiplet-major). With default XY routing the traffic is direction-symmetric (Darknet19 b1: 61.3 MB vs 61.7 MB), so a ≈ c is selected and gains are small.

L1Ring-flow SA operator

New SA move guided_ring_flow (48 options: direction × 8 ring offsets × mode). It lays consecutive pipeline stages along the ring (mode placement) and/or chooses DRAM read/write homes so that DRAM streams run in the ring direction (mode DRAM).

L2Per-transfer XY/YX route choice

Gemini only routes XY. A transfer from chip 4 to chip 3 then uses four hops of the narrow direction; YX uses the wide ring. Each transfer takes whichever of XY/YX follows the chosen ring (source routing, independent of link widths). Darknet19 b1 traffic becomes 82 MB vs 26 MB, and c ≫ a designs start to win.

L3Multicast ring forwarding

A multicast (e.g. one DRAM read broadcast to several chips) is forwarded destination-to-destination along the ring instead of a tree, so broadcast traffic also uses only the wide direction. Assumption: destination cores can forward; serial forwarding latency is not modeled by Gemini.

L4–L6Hardware–mapping alternation

The SA mapper adapts to the HW it searches on. L4 repeats all searches on a second asymmetric HW; L5 searches again on the currently best widths and adds route scope (route choice on DRAM-only or core-only traffic); L6 searches every batch again on the workload’s best common HW, so a batch that loses there can get a mapping fitted to it (LSTM b16: −11.9% → +0.6%).

Selection rule (best-effort mapping)

  • For each HW, each (workload, batch) uses its fastest mapping from every method’s pool — e.g. route choice at b1 and ring placement at b16. The uniform HW gets exactly the same choice.
  • Common HW (one design for batches 1/4/16): no batch may be slower than uniform; among those, prefer mean ≥ 10% and max ≥ 20%, then the highest mean. If no asymmetric design keeps every batch ≥ 0%, uniform is kept (0%). Groups (CNN/RNN/Transformer/ALL14 (all but RNN)) apply the same rule to all (workload, batch) pairs.
  • Selected designs are re-simulated natively (oracle/native parity checked). “Provisional” rows are oracle-only until that check.

Ring-forwarding sensitivity

Gemini models links by bandwidth only, so destination-to-destination multicast forwarding (L3) costs no extra time. Each model below re-selects both sides fairly (best mapping per side; common HW chosen with no slower batch). 4 chunks is the main evaluation model.

  • Free: original selection (forwarding has no cost).
  • 16 / 4 chunks: the message is forwarded in 16 or 4 pipelined chunks: Σ steps (size/C)/width + (C−1)·slowest step.
  • Store-and-forward (1 chunk): a chip forwards only after receiving the whole message — worst case.
  • No forwarding: forwarding variants removed from both sides — lower bound independent of the assumption.
